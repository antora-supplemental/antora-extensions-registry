Principles and decisions

Core call

Index everything, show what earned it. The registry knows about every Antora extension and theme it can find, but default results only show items that passed graduation or were grandfathered. Everything is security-scanned on every update.

  • Accounts are for using, not only uploading: Sign-in unlocks collections, stacks, ratings, flags and claiming. Sign-in copy: "Sign in to save collections, build a stack, and rate extensions."

  • Maturity is a registry status, not a semver claim: A 1.0.0 tag never promotes anything; graduation checks do.

  • Rating and quality flag are independent signals: Stars measure liking; flags measure craft. Popular-but-ugly can still be sequestered.

  • Thresholds need a minimum count and a rate: Small numbers alone can never crown or condemn an item.

  • Community polices quality; admins rule on disputes: No admin gate at graduation. Admins confirm Low quality, reinstatement and security blocks.

Accounts, collections and stacks

Concept What it is Visibility

Collection

Bookmark list of any items (extensions, themes, stacks)

Private by default; shareable link optional

Stack

Ordered set of extensions plus at most one UI theme, each pinned to a version range, with optional config snippets

Private draft, unlisted link, or published

Published stack

A stack listed in the catalog, rateable, forkable

Public; subject to the same flag rules

A stack member can be a registry item or any npm package or git URL. An unknown reference is ingested automatically (see Indexing) and becomes an Indexed listing; the stack links to it immediately while its first scan runs. Validation on save: every member resolves, no duplicates, one theme max, a warning for Workshop, Indexed or Low-quality members. Published stacks cannot contain Low-quality or security-blocked members.

Stack install CLI

Decided: a dedicated command, antora-registry, published in the npm package @antora-supplemental/registry. The scope is only the package name; the command is always typed as antora-registry. The scope stays unless Antora proper adopts the project. Every stack page also offers a no-CLI fallback (copyable snippet).

Install once (primary)

npm install -g @antora-supplemental/registry

Then run

antora-registry install <stack>

One-off, no install

npx @antora-supplemental/registry install <stack>

Command Effect

antora-registry install @ryan/docs-starter

Resolve stack, add npm deps to package.json, merge antora.extensions and ui.bundle.url into antora-playbook.yml (idempotent)

antora-registry install <stack> --dry-run

Print the diff only

antora-registry install <stack> --playbook site.yml

Target a specific playbook

antora-registry add <extension>

Add one item without a stack

antora-registry snapshot

Write antora-registry.lock.json with resolved versions for reproducible CI

  1. Fetch manifest: GET /api/stacks/:owner/:slug/manifest.json (public, versioned, cacheable).

  2. Resolve: Pin to semver ranges; warn on Workshop, Indexed, Low-quality or scan-warned members; refuse blocked ones.

  3. Write: Use a YAML CST editor (the yaml package Document API) to preserve comments; never clobber existing entries; ask before replacing a theme.

  4. Install: Run the detected package manager (npm, pnpm, yarn, bun) unless --no-install.

  5. Report: Print what changed and ping an install counter (opt-out via --no-telemetry); signed-in installs count toward the flag-rule denominator.

Recommendation: a separate Indexed state

Unclaimed ingested items get their own Indexed state, not Workshop. Workshop means a person is working on it and chose to be here; Indexed means the registry found it and nobody has spoken for it. Indexed items are findable by name so stack references and search work, but stay out of default browse and quality sorts. An Indexed item leaves the state by being claimed (goes to Workshop, or straight to Listed if the claimant marks ready and checks pass), or by community nomination. Decided: one nomination is enough, either a signed-in user’s published stack including it or an explicit Nominate for listing click, provided the security scan passes (pass or warn). The item moves to Listed unclaimed. The nominator must meet the flag/rate eligibility (account 7+ days, verified email, linked GitHub/GitLab 30+ days) and cannot own the item.

Indexing everything Antora

Goal: the registry knows every Antora extension and UI theme, whether or not it was built for the registry. A daily crawl (every 24 hours) plus event-driven ingestion feed one pipeline.

Source What it matches

npm search

Keywords antora, antora-extension, antora-ui; packages depending on @antora/*

GitHub / GitLab topics

Existing topic discovery (antora-extension, antora-ui, etc.)

GitHub / GitLab code search

register exports calling this.on('contentAggregated' (or other Antora events); ui-bundle layouts (src/partials, ui.yml, gulpfile with @antora/ui-default patterns); supplemental-ui folders

Playbook mining

antora-playbook.yml files: each antora.extensions entry and ui.bundle.url is a referenced item to ingest (the playbook repo itself is not a listing)

Registry references

Stack members and listing dependencies (e.g. a re-theme’s base theme) that are not yet in the registry

Manual and URL-expedite submissions

As before

  1. Normalize: Resolve to a canonical identity: npm name and/or repo host + numeric repo ID; merge npm and git records for the same project.

  2. Classify: Extension, UI theme, or not a listing (playbook sites, docs repos). Heuristic score; low-confidence matches go to an admin triage list instead of the catalog.

  3. Create Indexed listing: Set first_listed_at, record every ingestion_source, state Indexed, unclaimed.

  4. Scan: Run the security scan; Quarantined if blocked.

  5. Screen and outreach: Run graduation checks to build the public screening report; if registry files are missing, queue an outreach PR/MR.

Limits: GitHub code search allows about 10 requests per minute per token, so the crawl walks queries incrementally and stores cursors; npm search pages are cached for 24 hours. Forks are ingested only if they are published to npm separately or referenced explicitly.

Policy and etiquette risk

Unsolicited automated PRs can read as spam and can get a bot account flagged by GitHub or GitLab. GitHub Apps cannot open PRs on repos where they are not installed, so the decided dedicated machine user forks and opens PRs; naming the org, real maintainers and a Discussions link makes the bot accountable.

Claim ownership

  1. Click Claim this listing: Shown on every unclaimed listing and linked from the outreach PR.

  2. Verify via OAuth: GitHub: the signed-in user’s token shows admin or maintain permission on the repo. GitLab: access level Maintainer (40) or higher.

  3. npm-only packages: No npm OAuth exists, so the user adds a registry-issued token to the package’s package.json (antoraRegistry.claim) and publishes; the registry checks the published manifest and the npm maintainers list.

  4. Grant control: Claimant becomes owner: edit metadata, mark ready, request redemption, trigger scans, manage co-owners. Indexed listings move to Workshop.

Disputes (two claimants, or a transferred repo) go to the admin queue; ownership is re-verified when repo permissions change or once a year.

Security scanning

Every listing is scanned on every update: on demand when an owner publishes or clicks Scan now, and at worst in the nightly scan, which picks up any new npm version or default-branch commit since the last run, plus re-checks all listings against newly published advisories.

Check Method

Dependency advisories

OSV.dev batch query and npm audit data for the full resolved tree

Install scripts

Flag preinstall, install, postinstall scripts in the package and its deps

Obfuscated or minified source

Entropy and line-length heuristics on shipped JS that is not a declared build artifact

Network at build time

Run the install test in a sandbox with egress logged; any call outside npm registry and git hosts is reported

Secrets

gitleaks over the package tarball and repo head

License

SPDX license present and OSI-approved; mismatch between package.json and LICENSE

Known-malicious names

Match against OSV malicious-package (MAL) entries

Typosquats

Edit distance 1 to 2 from popular Antora packages (@antora/*, top 100 listings)
Outcome Effect

Pass

Nothing shown beyond a scanned date

Warn

Warning shown on the listing and in the CLI (e.g. postinstall script, moderate advisory, unexpected network call)

Block

Auto-Quarantined, install refused by the CLI, admin alert email to support@antora-supplemental.org; owner notified

Block triggers: critical advisory with no fixed version in range, malicious-package match, leaked live secret, or exfiltration-like network call. Owners can appeal by pushing a fix (see Security appeals and bans); admins can also clear a block with a reason.

Scan report page

Public page per listing (/x/:slug/screening): latest scan, findings by severity, graduation check results, history of runs. Linked from the outreach PR and the listing.

Where it runs

GitHub Actions in a registry-owned public repo (free minutes for public repos), triggered by Netlify functions via workflow_dispatch; Netlify functions are too short-lived for installs.

Cost

Expected $0 at current scale: Actions on a public repo and OSV are free; Turso storage of findings is small

Rate limits

On-demand: 1 scan per listing per 10 minutes, 20 per account per day; nightly batch capped by Actions concurrency

Security appeals and bans

Assume a mistake, not malice

Most blocks come from something committed by accident: a leaked key, a vulnerable dependency, a leftover script. Copy is non-accusatory: "Our scanner found something that needs a fix before this can be installed." Never "malicious" unless admins have decided so.

  1. Fix first: The owner pushes a commit that removes or fixes the flagged code (and rotates any leaked secret).

  2. Appeal = resubmit: Owner clicks Appeal on the screening page, naming the fix commit SHA. The full scan reruns on that SHA; if it passes, the block clears automatically and the appeal closes as resolved.

  3. One queued appeal per item: While an appeal is open, Appeal is disabled. A new appeal needs a new commit SHA.

  4. Admin review: If the rescan still blocks, or the owner disputes a finding as a false positive, the appeal goes to admins under the verdict rules (lifting a quarantine needs a second admin once there are 2+).

  5. Outcome: Accepted: back to prior state. Rejected: stays Quarantined, with the reason and what to fix.

Bans

Trigger

More than 5 rejected appeals (the 6th rejection) across all items the user owns; auto-resolved appeals do not count

Scope

The user account and items they solely own: items hidden, no new submissions, claims, ratings, flags or stacks. Items with other verified co-owners stay up under those co-owners

Org risk

Org-owned items are not banned with the user; the user loses rights on them. Banning a whole org needs a separate admin verdict, since one member could otherwise take down a shared namespace

Unban appeals

1 every 3 months (next_unban_eligible_at)

Unban review

Decided by the admins who rejected the counted appeals, voting together; must be unanimous

Missing reviewers

Decided: remaining rejecting admins plus one replacement admin chosen at random from eligible admins (not involved in the case, not recused), still unanimous

Agentic AI reviewer

A prompt-only LLM is unreliable for judging intent, because investigating means acting: cloning the repo, diffing versions, rerunning scanners, reading commit history. So the reviewer is an agent with tool access, running in a sandbox with no secrets and logged egress. It gives an advisory verdict (likely mistake, unclear, likely malicious) with evidence; admins decide.

Cost control Rule

Static scanners on every update; AI only on escalation (a block or an appeal sent to admins); never on routine updates

Decided: trust is granted, never self-nominated

Trust is a relationship between the antora-supplemental team and the requester, so only registry admins grant it, under the admin verdict and quorum rules. An org or user may ask through the /trust form, but cannot nominate itself. An admin who is a member of the requesting org or is the requesting user is recused and cannot propose or vote on that grant; if recusal leaves no eligible admin, the request waits.

Trust requests

  1. Submit /trust form: Signed-in user requests permanent pre-approval for their account or an org/group they belong to (membership verified via the provider API), with an optional note. One open request per subject.

  2. Store and notify: Insert a trust_request row and email support@antora-supplemental.org via Resend.

  3. AI pre-check: The agentic reviewer inspects the requester’s repos, publish and commit history and past registry record, then saves an advisory recommendation (grant, unclear, decline) with evidence on the request. Same sandbox and budget caps as security reviews; skipped if the budget is spent or AI is disabled.

  4. Admin verdict: Admins see the full report and decide under the verdict and recusal rules (trust_grant verdict).

  5. Tell the requester: Outcome plus a short summary of the report; evidence details stay admin-only.

No PR to any repo is needed. Optional later variant: a GitHub issue in the registry repo triggers the same AI check and hosts the public report as a comment, for requesters who prefer a public record.

Ratings and quality score

Users rate 1 to 5 stars (one rating per account per item, editable; latest wins). Map to p = (stars − 1) / 4 in [0, 1]. For a selected window, sort by a Bayesian average pulled toward the catalog mean, and display the raw mean with a confidence cue.

Score = (C·m + Σ pᵢ) / (C + n)

m is the catalog-wide mean p in the window, n the number of ratings in the window, C = 10. In plain terms: every item starts as if it had 10 average ratings, so a handful of 5-star votes cannot jump it past a well-rated, heavily used item.

Precise fill

Stars filled to the raw window mean, e.g. 3.73 / 5 = 74.6%

Confidence

Fill opacity scales with n (full at n ≥ 30); label shows "74.6% · 12 ratings"

Sort key

Bayesian score, so 1 rating of 5 stars never outranks 80 ratings at 4.6

Time window

Ratings filtered by created_at in [start, stop]; edited ratings count at their edit time

Low-quality flags

Reports and admin notification

Decided: every flag or report on an extension or theme is a report with a reason and an optional message. It is stored in the admin report queue, and each new report emails support@antora-supplemental.org.

  1. User submits: Reason (required) plus optional message, in the flag dialog.

  2. Store: Insert a report row (status open) and, for low-quality reasons, the flag row, in one transaction.

  3. Notify: Enqueue an outbox email to support@antora-supplemental.org via Resend: item, reason, message, reporter handle, admin queue link.

  4. Triage: Admin resolves or dismisses with a reason; status becomes resolved or dismissed.

Redemption review

  1. Owner requests re-review: Requires a new release since the Low-quality verdict and a changelog note addressing cited reasons.

  2. Automated review: Security scan, graduation checks and install test; failure stops here with the owner told why.

  3. Admin queue: Entry with flag reasons, release diff, automated results.

  4. Flagger panel: Email up to 100 random subscribed flaggers. Each answers: Is this now acceptable quality? Yes / No / Can’t tell.

  5. Decide: Statistical rule below produces a recommendation; admin verdict is final.

Response bias

Flaggers are harsher than average, so their approval is strong evidence; that justifies a simple-majority bar. Expect about 5 responses per 100 invites.

Burst of flags (more than 3x the item’s 30-day daily mean) from new accounts is held for admin, not counted

User flows

Flag dialog

  1. Click Flag as low quality: Only on Listed items; ineligible accounts see why.

  2. Pick reason + optional message: Flags are about craft, not taste; use stars for taste. Message is plain text, up to 2,000 characters, seen only by admins.

  3. Redemption checkbox, pre-checked: "Notify me if the developer asks for a second look." If the email category is off, show an inline toggle to enable it.

  4. Confirm: Insert flag, report and redemption_subscription in one transaction; show undo.

Review request (owner)

  1. Item dashboard shows status, scan results and cited reasons: Aggregated reason counts, never flagger identities.

  2. Request re-review: Enabled once a newer release exists; changelog note required.

  3. Track progress: Automated result, panel response count, admin decision.

Admin queue

One list sorted by age, filterable by kind (flag, redemption, scan block, claim dispute, ingest triage). Each entry: item preview, status history, flag count and share, panel posterior, scan findings, and actions Confirm / Dismiss / Reinstate / Extend panel / Clear block / Remove, each requiring a reason.
